---
name: visual-grounding
description: Build visual systems from semantic structure and verify the rendered output. Use only when explicitly requested.
disable-model-invocation: true
---

Start with a cold look at the actual output. Inspect native-size frames and a contact sheet before reading the source or prior audits. When the work is consequential, ask independent cold reviewers to name what looks wrong at a glance. Treat ambiguity, weak hierarchy, apparent misalignment, and accidental symbols as defects even when a coordinate check passes.

Model the subject before drawing it. Name its entities, states, events, routes, boundaries, branches, and outcomes. Define a skeleton of rails, lanes, stations, and crossings that expresses those relationships. A scene should place a mark by a named anchor, not by its own x/y, CSS offset, or transform. Put viewport mapping and size tokens in one layout adapter. Check a focused visualization library before writing layout or path machinery yourself; import the useful module when it makes the model simpler. A library does not supply the subject's ontology for you.

Choose a small visual vocabulary for the subject, then use each form consistently. A circle is useful when a state or event really reads as a point; a record, clock, gate, or document may need a different form. Do not turn every concept into the same target, badge, or polygon. Avoid ridges, extra rings, and decorative marks that have no role in the explanation. Use scale, spacing, contrast, and motion to make the important relationship legible before adding labels.

Make each visual object indivisible. Its glyph layers, label, status, and motion target belong to one owner group. Concentric parts share one local origin and one transform. Draw connections to named boundary ports; do not let a rail show through a hollow mark or stop in unexplained space. Animate the owner group along a route generated by the same skeleton. Do not independently animate an inner ring, token, or label with a bounding-box transform origin.

Make invalid relationships unavailable in the scene API. An absent event cannot originate a recorded-event route. A held item cannot acquire an outcome edge that requires completion. A label cannot exist without an owner. Prefer constructors and generated output that cannot express these contradictions over comments or a validator that merely catches them later.

Fix failures at the broadest level that explains them. Before adding a size, spacing option, glyph variant, or film-specific exception, check whether the skeleton, ownership rule, port geometry, or viewport adapter is wrong. Keep a new option only if it describes a reusable visual role and works across different scenes and viewport scales. Delete one-off offsets and patches after the structural fix lands.

Verify three different claims: the scene model has the intended topology; the runtime pose preserves its owner relationships; the encoded pixels read correctly. Use tests that can fail for route endpoints, owner and label movement, concentricity, clearance, and state reachability. Sample stable poses and both sides of transitions. Measure visible centers when alignment is in doubt, but judge the image's meaning, scale, contrast, and rhythm as well. Revise the model or glyph grammar when a bad image is faithfully rendered from bad semantics. Finish by checking the delivered artifact, not just the source or preview.
